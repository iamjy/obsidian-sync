# 소프트웨어 아키텍처 vs 상세 설계
## 1. 관계 및 정의
- **관계**: 소프트웨어 아키텍처는 설계(Design)의 한 부분이며, 별개의 개념이 아닙니다.
- **구분 목적**: "누가 어떤 결정을 내려야 하는지"에 대한 **역할과 책임**을 명확히 하기 위함입니다.

## 2. 결정 범위와 특성
| 구분        | 소프트웨어 아키텍처          | 상세 설계                 |
| :-------- | :------------------ | :-------------------- |
| **영향도**   | 시스템 전체에 영향          | 국소적인 기능 구현에 영향        |
| **관리 방식** | 명시적으로 다루고 기록해야 함    | 아키텍트의 개입 없이 자율적 진행 가능 |
| **핵심 요건** | 아키텍처 원칙 준수 여부 확인 필요 | 세부 구현의 효율성과 정확성       |

## 3. 구분하지 않았을 때 발생하는 문제
- **아키텍트가 모든 설계에 개입할 경우**: 개발자의 자율성이 침해되며, 아키텍트가 프로젝트의 **병목(Bottleneck)**이 됩니다.
- **구분이 전혀 없을 경우**: 중요 결정이 임의로 내려져, 나중에 되돌리기 어려운 치명적인 결함들이 '조용히' 쌓여 시스템을 망가뜨릴 수 있습니다.

아키텍처 설계 vs 상세 설계 - 구분 기준 3가지
어떤 설계가 아키텍처이고, 어떤 설계가 상세 설계일까?
세 가지 기준으로 구분한다.
1) 영향 범위
   아키텍처 설계: 시스템 전체 또는 여러 팀에 영향, 컴포넌트 간 관계와 경계를 결정
   상세 설계: 특정 모듈 클래스 수준에 머무름, 컴포넌트 내부 구현을 결정
2) 변경 비용
   아키텍처 설계: 변경 시 큰 비용이 든다. 시스템 전체를 수정해야 할 수도 있다.
   상세 설계: 상대적으로 빠르게 수정 가능. 해당 모듈만 수정하면 됨.
3) 추상화 수준
   아키텍처 설계: 구조와 관계 - 시스템을 조망하는 수준
   상세 설계: 클래스 메서드 - 코드에 가까운 수준
4) 예시
   아키텍처 설계: MSA를 선택하는 것. Layered 아키텍처를 선택하는 것. 모놀리식 구조 -> MAS로 전환하는 것
   상세 설계: 특정 화면의 UI 레이아웃을 설계하는 것. 클래스를 여러 클래스로 분리하는 것. 메서드 내부 로직을 어떻게 구현할지 결정하는 것

"모든 아키텍처는 설계이지만, 모든 설계가 아키텍처는 아니다."

설계란, 소프트웨어를 만들기 전에 "어떻게 만들 것인가"를 결정하는 모든 활동이다.

소프트웨어 설계: "어떻게 만들것인가?"
아키텍처 설계: 시스템 전체, 큰 변경 비용, 품질 속성
상세 설계: 컴포넌트 내부, 클래스, 메서드, 패턴

아키텍처는 "중요한 것"에 관한 것이다.
"중요한 것"은 바로 **나중에 바꾸기 힘든 설계 결정**이다.
모든 설계가 아니라, **바꾸는 데 큰 비용이 드는 정말 중요한 설계가 아키텍처**이다.
