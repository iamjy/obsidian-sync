louis님, **평가 방향은 맞습니다. 다만 현재 보고서는 후보 SSD의 이상 징후를 찾는 스크리닝 자료로는 유용하지만, Orin NX/Nano 양산 SSD를 선정할 근거로는 부족합니다.** 지금 우선할 일은 재부팅 횟수를 더 늘리는 것이 아니라, **양산 보드에서 부팅 실패도 빠짐없이 기록하고, BIWIN NV7200에서 관측된 연속 성능 급락을 확인하는 것**입니다.

첨부 엑셀의 원자료 **7,000행**과 부팅 상세 **1,000행**을 독립 재집계했고, 주요 판정 수식은 합성 반례로 재계산했습니다. 원본은 수정하지 않았습니다.

## 1. 데이터가 실제로 말해 주는 것

| 모델 / DUT | 조건 | 기록된 재부팅 / FAIL | 부팅 지표 평균 / 최대 | 평균 / 최소 IOPS | 사이클 평균 지연의 최대 |
|---|---|---:|---:|---:|---:|
| 990 EVO Plus / `EVO-03` | C | 3,000 / 0 | 70.57 / 73.06초 | 195,662 / 130,560 | 0.249ms |
| 990 Pro / `PRO-02` | B | 3,000 / 0 | 70.53 / 73.06초 | 201,295 / 127,566 | 0.252ms |
| BIWIN NV7200 / `NV72-02` | B | 1,000 / 0 | 15.75 / 76.13초 | 156,252 / **1,435** | **22.294ms** |
| Crucial P510 | — | 미측정 | — | — | — |

부팅 지표는 **전원 인가부터 앱 준비 완료까지의 시간**이 아니라 스크립트가 읽은 `/proc/uptime`입니다. 지연 열 역시 **개별 I/O의 최대 지연**이 아니라 **각 사이클에서 측정된 평균 지연 중 최대값**입니다.

가장 중요한 발견은 **NV7200의 788~791회차**입니다. 4회 연속 **1,435~1,436 IOPS, 평균 지연 22.273~22.294ms**였고, 792회차에 **170,403 IOPS / 0.187ms**로 돌아왔습니다. 네 회차 모두 `PASS`였습니다. 현 수식은 전체 평균을 보기 때문에 이 구간이 판정에 반영되지 않습니다. 당시 기록에서 `snapd.seeded.service`와의 동시 관측은 확인되지만, SSD·백그라운드 부하·전원관리·계측 중 어느 것이 원인인지는 확정할 수 없습니다. **NV7200은 탈락이 아니라 원인 확인 전 보류**가 타당합니다. (`03_RawData!6791:6795`, `03C_부팅상세!818:822`)

## 2. 양산 결정을 막는 세 가지 문제

1. **부팅 `합격`이 실제 시험 범위보다 넓습니다.** 보고서의 `09_평가매트릭스!C16`에 따르면 스크립트는 `reboot`만 호출합니다. 그런데 평가표는 *Cold Boot / Warm Reboot*를 한 항목으로 묶어 `합격`을 표시합니다. 부팅하지 못해 스크립트가 시작되지 않은 시도는 이 엑셀만으로 집계 여부를 확인할 수 없습니다. 따라서 **`기록된 warm reboot에서 FAIL 0건`**은 말할 수 있지만 **`전체 부팅 시도에서 실패 0건`**은 말할 수 없습니다.

2. **판정 수식이 미완주·미관측·꼬리 지연을 통과시킬 수 있습니다.** `04_DUT별요약!I41`은 목표 사이클 달성이나 실제 `PASS` 건수를 요구하지 않습니다. 원본 수식으로 합성 반례를 재계산하니, **같은 사이클의 중복 2행에 `UNKNOWN` / `NOT_RUN`만 있어도** 나머지 수치가 기준 안이면 `PASS`였습니다. `09_평가매트릭스!G7`도 DUT별 완주가 아니라 모델 합산 행수를 보는 탓에, **각각 600회인 DUT 두 대**를 1,000회 목표에 `합격` 처리합니다. 게다가 `02_판정기준`은 성능·온도 등 5개 임계값을 예시라고 명시하고, 목표 셀은 1,000회인데 주석에는 3,000회가 남아 있습니다.

3. **지금의 종합 순위로는 SSD 자체를 비교할 수 없습니다.** 계획된 **16개 모델×조건 중 3개**만 기록이 있습니다. EVO는 C, Pro와 NV7200은 B이고, 같은 B라도 보드·이미지·스크립트·실효 설정이 동일했는지 확인되지 않습니다. NV7200은 `v2.1` 재측정으로 명시돼 있고, 두 Samsung 결과와의 약 55초 차이를 SSD가 만든 차이라고 볼 수 없습니다. 전원관리도 EVO의 APST 설정은 `0us`, ASPM은 전부 `off`로 **기재**됐으며, NV7200의 `Wake_Detected` 31.8%는 지연 기반 간접 지표입니다. AER·링크 상태·쓰로틀링 기록은 없습니다. **모델 순위와 전원관리·열 ‘조건부 합격’은 참고로만 보세요.**

## 3. 다음 평가의 우선순위

| 우선 | 시험 | 확보할 양산 판정 근거 |
|---|---|---|
| **P0** | **양산 NX/Nano에서 기준품과 저가 후보를 동일 조건으로 비교** | 실제 출하 모듈·캐리어 리비전·전원·M.2 슬롯·JetPack/L4T·UEFI/QSPI·이미지·시험 스크립트를 고정합니다. AGX에서 쓰던 검증품이 양산 보드에 맞으면 대조군으로 옮겨 시험하고, NX와 Nano를 모두 출하한다면 각각 확인합니다. |
| **P0** | **초기 플래시·콜드 부팅·웜 재부팅을 분리** | 외부 시험기로 시도 ID를 먼저 남기고 **전원 인가 → UEFI에서 NVMe 인식 → 의도한 NVMe rootfs 확인 → 앱 ready**를 기록합니다. 각 경로의 시간 제한과 허용 실패 기준은 제품 요구사항으로 확정합니다. 현장 업데이트·복구가 있다면 해당 경로도 확인합니다. |
| **P0** | **NV7200 급락 재현과 전원 차단 복구** | 급락 재시험은 기준품과 동일 이미지에서 `fio` 원본, 커널 로그, SMART, 서비스 타임라인을 함께 남깁니다. 전원 차단은 별도 승인된 시험 환경에서, 정상 콜드 부팅과 별개로 쓰기·부팅·업데이트 중 차단 후 **이미 영속화된 데이터의 무결성과 복구 가능 여부**를 확인합니다. |
| **P1** | **실부하·열·수명·구매 검증** | 현재 `10초 / 100M` fio는 유지하되 스크리닝으로만 사용합니다. 최종 후보는 실제 케이스에서 제품 부하·높은 채움률·지속 쓰기로 지연 꼬리와 쓰로틀링을 측정합니다. 실사용 쓰기량 대비 TBW, 정확한 부품번호·펌웨어·로트, 실장 간섭, 양산 단가·공급·BOM 변경 통지 조건도 확인합니다. **필수 기준을 통과한 후보끼리 가격을 비교**하는 편이 안전합니다. |

NVIDIA의 [Jetson Linux r36.4.4 Quick Start](https://docs.nvidia.com/jetson/archives/r36.4.4/DeveloperGuide/IN/QuickStart.html)는 NX/Nano 양산 모듈에서 QSPI-NOR와 외부 NVMe를 사용하는 구성을 안내합니다. [커스텀 캐리어 가이드](https://docs.nvidia.com/jetson/archives/r36.4.4/DeveloperGuide/HR/JetsonModuleAdaptationAndBringUp/JetsonOrinNxNanoSeries.html)는 캐리어에 맞춰 부팅 설정과 PCIe 구성을 조정하도록 합니다. 즉, **AGX에서 SSD가 잘 동작했다는 이력은 대조군을 고르는 근거이지, 양산 캐리어에서 부팅이 보장된다는 근거는 아닙니다.**

**현재 의사결정 권고:** 990 계열은 대조군 후보로 유지, NV7200은 급락 재시험 전까지 보류, P510은 미평가로 두세요. 보고서의 전체 상태는 `양산 승인 진행중`보다 **`warm reboot 스크리닝 결과 확보 / 양산 적격성 미확정`**으로 적는 게 정확합니다. 이번 검토는 문서·데이터·수식 검증이며, 실제 보드 시험이나 `boot_aging_test.sh` 원본 검증은 포함하지 않았습니다.

재집계 수치, NV7200 이상 회차, 판정 수식 반례, 다음 시험의 합격 기준 초안을 별도 파일에 정리했습니다.
